# ADR 0001：独立 Dot 后端与 QQBridge 适配边界

- 日期：2026-10-25
- 状态：已采纳；真实联调结果见 [验证记录](../verification.md)
- 初始交付：离线生命周期原型；后续实现进展见文末

## 背景

目标是在已有 SnowLuma + QQBridge `reserved2` 仿真群友模式上接入 ChatGPT Dot，继续使用 QQBridge 的消息收发、每群状态、角色、唤醒规则和发言节奏。

检查的上游基线是 [`Derpyu520/qq-bridge@a49877f4e58d04e47532d44b803360d0f001160d`](https://github.com/Derpyu520/qq-bridge/tree/a49877f4e58d04e47532d44b803360d0f001160d)。该版本的唤醒投递依赖 DSH 会话 API，忙碌和回合收尾依赖 DSH 事件；现有 QQ MCP 是由 DSH 启动的本地 stdio 服务。它没有可以直接配置使用的 Dot 后端入口。

源码依据：[`src/bridge.js`](https://github.com/Derpyu520/qq-bridge/blob/a49877f4e58d04e47532d44b803360d0f001160d/src/bridge.js)、[`src/mcp-snowluma-safe.js`](https://github.com/Derpyu520/qq-bridge/blob/a49877f4e58d04e47532d44b803360d0f001160d/src/mcp-snowluma-safe.js)。

## 决策

以独立仓库维护 Dot 后端和它的协议、状态机及测试；QQBridge 端另需与指定上游 commit 绑定的适配改动。本项目不承诺原版 QQBridge 零改动接入。

职责分配如下：

| 组件 | 职责 |
|---|---|
| SnowLuma | QQ 客户端接入与 OneBot 消息收发 |
| QQBridge | 会话白名单、消息入库、角色和群聊状态、唤醒合并、观察计时、限频及实际发信 |
| 本项目 | Dot 后端协议、事件投递适配、运行代际和回执、远程工具边界及故障恢复 |
| ChatGPT Dot | 根据收到的会话上下文决定发言、安静完成或继续观察，通过受限工具提交动作 |

每个 QQ 会话同一时刻只由一个后端处理。Dot 的任务完成与 QQ 消息发送分别记录；决定不插话也可以完成本轮，不能用“是否发过消息”代替完成回执。

## 必须保留的语义

1. 消息先进入 QQBridge 的会话状态，由既有规则合并后唤醒；不逐条创建 Dot 任务。
2. 事件接收成功只表示已投递。确认已读必须携带模型已看到的连续消息水位，不能清掉处理期间新到的消息。
3. 发信和完成回执绑定会话、运行 ID 与代际；重复调用保持幂等，旧运行不能覆盖新状态。
4. 保留白名单、会话范围、暂停、静默、限频和发送前检查。远程工具不能退化成控制台管理通道。
5. 观察与潜水仍由本地桥接维护。Dot 任务可以在等待期间结束，但不能因此跳过现有观察条件。
6. DSH 的会话 ID 和完整历史不自动迁移为 Dot 会话；QQBridge 已保存的角色、最近消息和群聊记忆可作为显式上下文。

## 为什么这样选

独立仓库便于将 OpenAI 接口变化与 QQ 客户端、QQBridge 的更新分开维护。直接 fork 更便于首次修改上游，但会同时承担整个桥接应用的更新；本方案将上游改动限制为后端选择、投递、生命周期和授权状态的必要边界。

这项选择也带来成本：上游目前没有稳定的后端扩展契约，适配范围尚不能保证很小。必须维护基线、补丁和集成验证；若边界持续扩大，需要重新评估是否将 QQBridge fork 作为主要集成载体。

## 当前范围与后续验收

`0.0.1` 交付离线生命周期原型；`0.1.0-experimental` 实现固定基线补丁、本地 API、安装器与组件测试；`0.3.1` 增加 MCP / Events、加密网关状态、纯 Dot 模式和 Windows 管理器，并完成一次真实私聊自动处理闭环。桥接运行账本的完整持久化恢复仍未实现。

后续只有完成“合并唤醒 → 获取对应会话上下文 → 可选择发言 → 按水位完成 → 再次唤醒”，并验证重复投递、旧回执、静默完成和观察等待后，才能声明支持指定 QQBridge 版本。详见 [QQBridge 兼容说明](../../compat/qqbridge/README.md)。
