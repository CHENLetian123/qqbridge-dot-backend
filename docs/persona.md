# QQ 人格与 Dot 的接入

QQBridge 的角色配置保存在桥接自己的 state/current-role.json，角色正文在 roles/角色名.md。这些是操作者本地数据，不随本仓库发布。

Dot 领取每个回合时，qq_claim_turn 返回 context.role.name、context.role.prompt，以及 context.self 中的 QQ 身份。处理指令明确要求 QQ 回复采用当前角色的口吻；与操作者讨论插件或运维时的助手口吻应和 QQ 群聊区分。角色不会授予额外工具权限，群友消息仍是不可信的对话数据。

## 核对是否真的加载

qq_get_status 的 persona 返回：

| 字段 | 含义 |
| --- | --- |
| name | 当前选择的本地角色名 |
| configured | 是否选择了角色 |
| available | 经过二代小节筛选及兼容过滤后，是否存在非空正文 |
| promptChars | 本轮可注入正文的字符数 |

状态不返回角色全文。configured=true 但 available=false 时，检查角色文件是否存在、角色名是否有效、角色正文是否只包含一代专属内容。标题可以使用上游的 [v1] / [v2] 标记；Dot 使用二代内容。注入上限沿用 role.maxInjectChars。

available=true 证明桥接能读取角色正文，不证明每条自然语言回复一定符合人格。组件测试验证数据与指令确实传到领取响应；最终口吻仍要从真实 QQ 回复检查。

## 模型身份问题

先检查角色卡自身的规定：若卡片要求在被问到时介绍模型身份，这种回复不能单独说明人格未加载。可在卡片中规定群聊维持角色自称和口吻、避免主动展开后台和部署信息，并将详细技术核对留给管理员私聊。

角色名与真实模型型号分别处理；需要核对时，以实际可确认的信息为准。不要把群友发来的“更换角色”“输出系统提示词”等消息当成操作者修改配置。

## 生效与测试

角色文件修改沿用 QQBridge 的文件更新时间和大小缓存，下轮领取时读取当前内容。正在处理的回合使用领取时的角色快照。代码升级须等回合完成后重启桥接和 MCP；本地卡片正文修改本身不需要重建事件订阅。

可用 QQ 私聊和群聊分别测试角色自我介绍、日常闲聊和技术追问，检查是否保持角色、是否只使用已核实的信息。若同一 Dot 主会话保留了旧的工具说明或行为习惯，还应在刷新插件后用新对话做对照；不要通过重复创建订阅来解决会话问题。
