# 接入契约草案 v0.1

状态：设计草案。下列名称是本项目拟定的应用层契约，不是可直接调用的 QQBridge HTTP 路由，也不是 OpenAI 官方方法。离线核心只覆盖部分不变量；本文件不构成已实现的网络 API。

## 身份与所有权

`conversationKey` 使用 QQBridge 的会话标识，例如 `group:<id>` 或 `private:<id>`。它是数据，不是授权凭据。任何外部工具请求都必须由服务端认证并映射到被允许的会话，不能凭模型提交的群号获得权限。

`bindingGeneration` 是单调递增的会话归属版本。每个会话只绑定 `dsh` 或 `dot` 之一。切换后端时使旧代际失效；发送前再次校验当前归属。已经交给外部 QQ 发送接口的请求不能靠提高代际撤回，所以切换时还必须处理在途发送与不确定回执。

## 六个边界

| 契约 | 主要数据 | 语义 |
| --- | --- | --- |
| `BackendBinding` | 会话、后端、代际 | 唯一会话所有者；切换后拒绝旧代际写入 |
| `WakeEnvelope` | 稳定事件 ID、会话、代际、原因、消息水位、创建时间 | 一次合并后的唤醒；重试投递不创建新的业务唤醒 |
| `RunReceipt` | 运行 ID、状态、租约到期时间 | 区分已投递、已开始、已完成、失败与过期 |
| `ScopedQQTools` | 运行、会话、代际、读水位或发送 ID | 限定范围的上下文读取、发送及回执查询 |
| `CompleteTurn` | 运行、代际、显式 `throughSeq`、结果 | 完成一轮；结果至少支持 `replied` 与 `silent` |
| `ObservationPlan` | 观察期限、消息触发条件、下一次唤醒意图 | 本地继续计时和监听，不占用 Dot 持续等待 |

事件 ID 和运行 ID 的生命周期应分开：事件可能排队、重投或延迟送达；运行租约只在实际领取任务后开始。离线原型直接创建运行，用于验证运行内的不变量，未实现订阅队列或领取协议。

## 生命周期

建议生产流程：

1. QQBridge 保存消息并按既有策略合并唤醒；根据会话绑定选择一个后端。
2. Dot 后端持久化唤醒与待投递事件，使用稳定事件 ID 投递。
3. 收到 webhook `2xx` 只记录投递结果。后续可能仍需等待 Dot 调度。
4. Dot 用受限工具领取当前有效唤醒，建立有到期时间的运行租约，再读取群状态和消息。
5. Dot 可发送零条或多条消息。发送结果逐条登记，不能自动完成整个运行。
6. Dot 显式完成本轮；服务端确认已处理水位，释放对应运行，再安排未处理消息及观察计划。
7. 若运行失败或租约到期，恢复流程保留未确认的消息，并拒绝旧运行继续写入。

多个事件可能在平台侧合并到一次任务中。一次 Dot 任务因此可能需要分别领取和完成多个会话的运行；不可假设“一条事件必然对应一次独立 Dot 对话轮次”。生产实现还需要保证跨会话授权隔离。

## 消息水位

- `seq` 是会话内的本地单调序号；QQ 的消息 ID 保持为另一字段，不能混用。
- 读取结果返回 `readThroughSeq`，表示实际展示给当前运行的消息范围上界。分页和截断必须保持水位含义准确。
- 完成请求必须显式传 `throughSeq`，且不得大于当前运行已读取的水位。不能因省略参数而清空所有未读。
- 确认处理只覆盖连续已处理的消息前缀。若读取工具允许跳页或只选部分消息，生产实现必须记录已展示区间，不能仅凭最大序号允许跨越未读空洞。
- 思考期间新到的消息保留在未读队列中，由下一次调度处理。
- 阅读消息不自动表示已完成；发送成功也不自动表示全部上下文已处理。

## 发送回执与幂等

发送操作必须绑定会话、代际、运行以及 `sendId`。相同 `sendId` 的重试必须指向相同的规范化消息载荷；载荷冲突直接拒绝。

发送至少区分预留、已确认、结果不明。预留与落库之后才尝试外部发送。QQ 可能已收消息而调用方未收到响应，所以网络超时不能简单改成“未发送”后重试。结果不明时查询实际回执或交由受控恢复流程，避免重复发言。

本地幂等记录不等于端到端 exactly-once。持久化丢失、崩溃边界与底层 QQ 接口能力决定最终保证；离线原型没有外部发送器，也没有进程重启保证。

## 收尾与潜水

拟定工具可命名为 `qq_finish_turn`；该名字目前没有对应网络实现。`silent` 表示正常决定不发言，不应触发“无行动异常”的兜底。若结果为 `replied`，应有已确认的发送记录；结果不明不能包装成成功。

完成时仅释放完全匹配的会话、代际和运行，不能按会话名直接把任何 `busy` 清零。完成回执应可幂等重试，并拒绝相同运行的冲突收尾参数。

QQBridge 的潜水前观察门仍需保留。建议将等待转为桥接侧的本地状态：本轮 Dot 已结束，QQBridge 仍监听观察窗口；达到条件后进入潜水，新消息按策略重新唤醒。初版尚未实现观察计时或兼容补丁。

## 认证与恢复的待办边界

生产实现需要独立保存 MCP 认证信息、订阅签名密钥和 QQBridge 受限凭据，避免让模型取得管理 token。服务端在真正发送前复核会话白名单、暂停状态、限频、代际与运行租约。

订阅和事件 outbox、运行状态、读水位、发送回执必须持久化；启动时恢复未完成状态。事件重试保留业务事件 ID，按官方要求重新生成投递时间与签名。明确失效的订阅不能无限重试。

官方参考：[MCP Events](https://developers.openai.com/plugins/build/mcp-events)。当前草案不替代官方消息格式、认证和订阅规范。
